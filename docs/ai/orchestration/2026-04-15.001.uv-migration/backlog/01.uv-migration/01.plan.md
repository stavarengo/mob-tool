# Plan: Migrate mob-tool to UV

## Linked backlog items

- BI-001: Remove legacy setup.py shim
- BI-002: Update .gitignore for UV conventions (remove `.python-version` from ignore list)
- BI-003: Add .python-version file (pin Python 3.11)
- BI-004: Generate uv.lock (run `uv sync`)
- BI-005: Update README development setup instructions
- BI-006: Migrate CI workflow to UV

## Problem and target outcome

mob-tool uses the legacy pip/venv/setuptools workflow for local development and the pip/build/twine workflow for CI publishing. This works but is slow, has no lockfile for reproducible installs, and requires multiple tools (pip, build, twine) where one (uv) suffices.

**Target outcome:** After this work item, the project uses UV as the sole frontend for local development (`uv sync`, `uv run`) and CI publishing (`uv build`, `uv publish`). setuptools remains the build backend. A committed `uv.lock` ensures reproducible installs. The `.python-version` file pins Python 3.11 for UV. The legacy `setup.py` shim is gone.

## Constraints and assumptions

- **UV is a frontend, not a backend.** The `[build-system]` section in `pyproject.toml` stays unchanged (setuptools). No metadata changes needed.
- **`pyproject.toml` is already canonical.** `[project]` metadata, dependencies, and entry points are all in `pyproject.toml`. The `setup.py` shim is dead weight.
- **Python version:** `requires-python = ">=3.11"` is already set. The `.python-version` file should pin `3.11` to match.
- **CI trigger:** The publish workflow triggers on pushes to `main` that change `pyproject.toml`. This trigger logic is unrelated to UV and should not change.
- **PyPI credentials:** The workflow uses `secrets.PYPI_PASSWORD` with twine. `uv publish` accepts the same token via `--token` flag or `UV_PUBLISH_TOKEN` env var.
- **No tests exist.** There is no test suite to break. Verification is limited to "does `uv sync` succeed, does `uv run mobt` work, does the CI workflow syntax validate."
- **No `requirements.txt` files exist.** Nothing to remove or migrate.

## Approach options

### Option 1: Minimal UV adoption (local dev only)

Replace only the local development workflow with UV. Keep CI using pip/build/twine.

- Remove `setup.py`, un-ignore `.python-version`, add `.python-version`, generate `uv.lock`, update README.
- CI stays as-is.
- **Pro:** Smallest blast radius. CI is untouched.
- **Con:** Leaves the CI workflow using legacy tools. Misses the main benefit of UV in CI (speed, single tool). Inconsistent: developers use UV locally but CI uses pip. Half-migration that will need a follow-up.

### Option 2: Full UV migration (local dev + CI)

Replace both local development and CI workflows with UV. All 6 backlog items.

- Remove `setup.py`, un-ignore `.python-version`, add `.python-version`, generate `uv.lock`, update README, migrate CI to `astral-sh/setup-uv` + `uv build` + `uv publish`.
- **Pro:** Complete migration. Single tool everywhere. No follow-up needed. CI gets faster installs. Consistent developer experience.
- **Con:** Slightly larger scope, but still small (the CI change is ~10 lines).

### Option 3: Full UV migration + pyproject.toml modernization

Everything in Option 2, plus modernize `pyproject.toml`:
- Pin dependency versions with `>=` ranges instead of `==` (let the lockfile handle pinning).
- Update GitHub Actions to latest versions (checkout@v4, setup-uv@latest).
- Add `[tool.uv]` configuration section.
- Upgrade Python pin to 3.12+.

- **Pro:** More "modern."
- **Con:** YAGNI. Changing dependency specifiers is a separate concern from UV migration. Upgrading Python is a separate decision. Adding `[tool.uv]` config is unnecessary unless there's something to configure. This overscopes the work item.

## Recommended approach

**Option 2: Full UV migration (local dev + CI).**

It completes the migration in one pass without overscoping. The CI change is straightforward and well-documented. Leaving CI on the old toolchain (Option 1) creates an inconsistency that will need a follow-up ticket, which is worse than doing it now given the small incremental effort. Option 3 bundles unrelated changes.

## Scope boundaries

**In scope:**
- Delete `setup.py`
- Remove `.python-version` from `.gitignore`
- Create `.python-version` with `3.11`
- Run `uv sync` to generate `uv.lock`
- Update README "Development Setup" section to use `uv sync` / `uv run`
- Update `.github/workflows/python-publish.yml` to use `astral-sh/setup-uv`, `uv build`, `uv publish`

**Out of scope (YAGNI / separate concerns):**
- Changing dependency version specifiers in `pyproject.toml`
- Adding `[tool.uv]` configuration
- Upgrading the pinned Python version beyond 3.11
- Adding dev dependencies or dependency groups
- Adding a `uv.toml` file
- Changing the CI trigger logic
- Adding new CI jobs (linting, testing)
- Changing `[build-system]` or migrating away from setuptools

## System impact

- **`setup.py`**: Deleted. No consumers depend on it; `pyproject.toml` is already the canonical config.
- **`.gitignore`**: One line removed (`.python-version`). No functional impact on other ignored paths.
- **`.python-version`**: New file, committed. UV uses this to determine which Python to install/use.
- **`uv.lock`**: New file, committed. Cross-platform lockfile for reproducible installs.
- **`README.md`**: "Development Setup" section rewritten. User-facing instructions change from pip to UV.
- **`.github/workflows/python-publish.yml`**: Build/publish steps change. Same trigger, same artifact (sdist + wheel uploaded to PyPI). The `PYPI_PASSWORD` secret is reused via `UV_PUBLISH_TOKEN` env var or `--token` flag.
- **`pyproject.toml`**: Unchanged. This is important -- UV works with the existing metadata as-is.

## Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| `uv publish` token format differs from twine | Low | CI fails to publish | `uv publish` accepts the same `__token__`-prefixed PyPI API tokens. Use `--token ${{ secrets.PYPI_PASSWORD }}` or set `UV_PUBLISH_TOKEN`. |
| `uv sync` fails due to dependency conflicts | Low | Blocks lockfile generation | Dependencies are already pinned with `==` and known to work together. If a conflict arises, it exists today too -- UV just surfaces it. |
| `astral-sh/setup-uv` action unavailable or broken | Very low | CI fails | Pin to a specific version tag (e.g., `v5`) rather than `latest`. |
| Developers without UV installed can't contribute | Medium | Friction for new contributors | README should mention `pip install uv` or `curl -LsSf https://astral.sh/uv/install.sh | sh` as a prerequisite. The old pip workflow still works if someone ignores the README, since `pyproject.toml` and setuptools are unchanged. |
| `.python-version` conflicts with pyenv users | Low | Minor confusion | UV and pyenv both read `.python-version`. Since the project already requires `>=3.11`, pinning `3.11` is compatible. pyenv users who already have 3.11 installed will see no difference. |

## Verification strategy

1. **Local verification:** Run `uv sync` in the repo root. Confirm `.venv/` is created, `uv.lock` is generated, and `uv run mobt --help` prints the CLI help.
2. **CI syntax validation:** Validate the updated workflow YAML is syntactically correct (well-formed YAML, valid GitHub Actions schema).
3. **README review:** Confirm the development setup section accurately describes the UV workflow with no references to the old pip/venv approach.
4. **File inventory:** Confirm `setup.py` is deleted, `.python-version` exists with content `3.11`, `.gitignore` no longer contains `.python-version`, and `uv.lock` exists and is non-empty.
